# T-006: Accept a YouTube link as POST /highlights input

Request R-002. Plan: `docs/superpowers/plans/2026-11-23-t-006-accept-a-youtube-link-as-post.md`.

## Product Owner request

API + web upload: POST /highlights nhận video hoặc link YouTube, trả về danh sách đoạn highlight, có trang xem trước và chỉnh mốc cắt bằng tay.

## Goal

Goal of R-002: a user opens a web page, uploads a video or pastes a YouTube link, sees the detected highlight segments next to a preview player, adjusts start/end by hand, saves, and gets clips re-cut at the new marks. It is done when TestClient tests cover upload→segments, URL→segments, segment edit→re-cut clips, and both pages are served. Approaches considered: (a) extend the R-001 FastAPI app with a `url` form field, JSON edit endpoints and one static vanilla-JS page served by FastAPI, (b) a separate React/Vite SPA with its own build, (c) Jinja server-rendered forms with full page reloads for every edit. We picked (a): no Node toolchain, everything is testable with pytest, and the processing stays synchronous like R-001 (YAGNI; async jobs only if real uploads time out). This task adds `sportscut/sources.py` with `download_youtube(url, dest_dir) -> Path`, using yt-dlp through a new `[youtube]` extra (Python API, `noplaylist`, format capped at 720p mp4 for the CPU budget, a max filesize and max duration of 3 h). Only http(s) URLs on youtube.com, www/m.youtube.com and youtu.be are accepted (this blocks SSRF). Failures raise `SourceError`, which maps to HTTP 400. `POST /highlights` then takes exactly one of multipart `file` or form field `url` (422 if both or neither) and stores `source_url` in the job. Tests monkeypatch the downloader to copy the synthetic video, so they need no network. Assumptions: this starts only after R-001's T-005 (`sportscut/api.py`, `pipeline.run`) is merged; if it is missing on the base branch, report BLOCKED instead of re-creating it. The PO is responsible for the rights to the linked videos. Not a quality change: no F1 gate (there is no eval yet), and it must not change detection output.

## Decisions

- T-006 (R-002): Starts only after T-005. Step 0 runs `test -f sportscut/api.py && grep -q '^def run(' sportscut/pipeline.py && grep -q '@app.post("/highlights")' sportscut/api.py && echo READY || echo BLOCKED`. If it prints BLOCKED, report BLOCKED and never recreate api.py or pipeline.run. T-007 (also edits api.py) runs after T-006, not at the same time.
- T-006 (R-002): `sportscut/sources.py` owns video sources: `SourceError`, `check_youtube_url(url) -> None` and `download_youtube(url, dest_dir) -> Path`. yt_dlp is imported only inside download_youtube, after URL validation. A missing import raises SourceError "YouTube links need the [youtube] extra: pip install 'sportscut[youtube]'". Importing sportscut.api or sportscut.cli never loads yt_dlp.
- T-006 (R-002): Allowed links: scheme http/https, hostname exactly one of youtube.com, www.youtube.com, m.youtube.com or youtu.be (case-insensitive), no userinfo, no explicit port, no control/whitespace characters or backslash, length <= 2048. Every rejection has the single message 'url must be an http(s) link to youtube.com or youtu.be'. The API validates the URL before creating a job dir or calling the downloader (SSRF guard), and download_youtube validates again.
- T-006 (R-002): yt-dlp options: format 'bv*[height<=720][ext=mp4]+ba[ext=m4a]/b[height<=720][ext=mp4]', merge_output_format mp4, noplaylist, max_filesize = MAX_DOWNLOAD_BYTES (2 GiB constant), outtmpl <dest>/source.%(ext)s, quiet, no_warnings, noprogress, cachedir False. The download is two-step: extract_info(download=False, process=False), checks, then process_ie_result(download=True). The output is always <dest>/source.mp4.
- T-006 (R-002): Only a single YouTube video is accepted: info _type must be 'video' (default) and extractor_key must be 'Youtube'. Live or upcoming streams, unknown duration and duration > 10800 s are rejected before downloading. A file larger than MAX_DOWNLOAD_BYTES is rejected after downloading. yt_dlp.utils.YoutubeDLError becomes SourceError('could not download video: <msg>') with the dest path replaced by 'download'.
- T-006 (R-002): POST /highlights takes exactly one of multipart `file` or form `url`. A blank or whitespace-only url counts as absent. Both or neither gives 422 'send exactly one of file or url', checked after FastAPI validation and before the min_len/max_len check. A SourceError gives 400 with str(exc), and the job dir is deleted. All T-005 status codes and the response body {job_id, highlights} are unchanged.
- T-006 (R-002): A URL job downloads into <job>/download/, then os.replace moves the file to <job>/input and the download dir is removed, so pipeline.run gets the same arguments as for uploads. Every successful job writes <job>/job.json = {"source_url": <url or null>} (UTF-8, trailing newline). It is never served: get_clip still serves only manifest names.
- T-006 (R-002): New extra `youtube = ["yt-dlp>=2024.8.6"]`. `dependencies`, `api` and `dev` stay exactly as T-005 pinned them. Tests use a fake yt_dlp module and a monkeypatched downloader, so the suite needs neither yt-dlp nor network.
- T-006 (R-002): The PipelineError detail keeps replacing the input path with 'upload' for URL jobs too. The PO is responsible for the rights to linked videos (stated in the README). Processing stays synchronous; async jobs come only if real downloads time out.
- Tech Lead (dev_blocked): T-006 must restart from the latest base after T-005 is merged because its required API and pipeline entry point are absent and the task was incorrectly scheduled with no dependency.
