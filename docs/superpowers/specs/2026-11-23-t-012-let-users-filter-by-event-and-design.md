# T-012: Let users filter by event and pick the top N in the CLI and API

Request R-003. Plan: `docs/superpowers/plans/2026-11-23-t-012-let-users-filter-by-event-and.md`.

## Product Owner request

Highlight theo sự kiện: gắn nhãn bàn thắng, cứu thua, thẻ đỏ, pha tranh cãi. Người dùng lọc "chỉ bàn thắng" hoặc "top 5 pha hay".

## Goal

Add `--events goal,save,...` and keep `--top N` on `sportscut cut`, with the same `events`/`top` fields on `POST /highlights` and an `?event=` filter on the job read. Ranking for 'top N' = segment score × an event priority (goal > red_card > controversy > save > other), so goals win ties. The result is still exported in time order. Output JSON and `highlights.json` include `event` and `event_confidence`. Filtering happens after classification and before export, so 'goals only' cuts only goal clips. Tests: hand-built segments with known events produce the right filtering and ordering; an unknown event name gives a CLI error / HTTP 422; filtering out every segment gives an empty list without crashing. Until the classifiers in tasks 4-6 land, everything is `other`, so this is plumbing only and must not change eval F1.

## Out of scope

- Event classifiers (audio shape, whistle, scoreboard change, red close-ups) and real event_confidence values; every segment stays 'other' with confidence 0.0
- Building tests/fixtures/eval or tuning EVENT_PRIORITY weights against precision_at_5
- --events on `sportscut detect` or `sportscut eval`; filtering by a minimum event_confidence
- An events selector or event badges on the web upload page (sportscut/web/), and the HTML `/jobs/{id}` page
- `top` or re-export on GET /highlights/{job_id}; re-cutting clips after the job was created
- Async jobs, persisting the requested filter in job.json, and pagination
- Using event_confidence in the ranking

## Decisions

- T-012 (R-003): Pipeline order is detect all candidates (`find_highlights(top=None)`) -> classifiers (`tag_goals` now fills this slot) -> filter by events -> rank and take top N -> export in time order. `top` applies after the filter, so 'top 5 goals' is the 5 best goals among all candidates. (updated by T-013) (updated by T-014: `tag_saves` runs immediately after `tag_goals` in the classifier slot)
- T-012 (R-003): `find_highlights(top=None)` means no cap (every non-overlapping candidate). Integer top keeps its exact old behaviour, and the eval keeps calling the default top=10, so eval F1 is unchanged.
- T-012 (R-003): Ranking lives in the new module `sportscut/ranking.py`: `EVENT_PRIORITY = {goal:5, red_card:4, controversy:3, save:2, other:1}`; the rank key is `(-(score*priority), -priority, start, end)`, so a goal wins a tie on score x priority and then the earlier segment wins; the result is returned sorted by (start, end). Scores are assumed to be non-negative (detector z >= 3). Weights may be retuned later only with an eval that shows precision_at_5 does not drop.
- T-012 (R-003): `parse_events(text)` splits on commas, strips and lower-cases, de-duplicates in first-seen order and returns a tuple. An empty or unknown item raises ValueError `unknown event '<name>'; choose from goal, save, red_card, controversy, other`. Input is case-insensitive, while Segment.event stays exact lowercase (T-010).
- T-012 (R-003): `Segment` gains the last field `event_confidence: float = 0.0` (0.0 = not classified), validated 0 <= c <= 1 (NaN rejected, message 'event_confidence must be between 0 and 1'). `to_dict()` emits it as the last key, so detect --json, pipeline.run entries and highlights.json gain it. This updates T-035 AC5, T-002 AC9, T-004 AC1 and T-010 AC1/AC2.
- T-012 (R-003): This reverses the T-010 decision that the POST /highlights response keys stay unchanged. Response items are now `{start, end, score, reason, event, event_confidence, clip_url}` in that order (updates T-005 AC2 and T-010 AC2). The API reads entries with `.get('event','other')` and `.get('event_confidence', 0.0)` so manifests written before T-012 still load.
- T-012 (R-003): `pipeline.run(..., events: Iterable[str] | None = None)`. `top < 1` raises PipelineError 'top must be >= 1' before require_ffmpeg. An unknown event from select_segments becomes PipelineError. Filtering out everything writes highlights.json `[]` and returns [] (no error).
- T-012 (R-003): CLI `cut --events` uses an argparse type that turns the parse_events ValueError into ArgumentTypeError, so a bad value exits 2 with `sportscut cut: error: argument --events: unknown event ...` before ffmpeg. 'Goals only' with no goals exits 0 with empty stdout.
- T-012 (R-003): `POST /highlights` gets form field `events` (comma list; blank = absent). It is validated after the exactly-one-source and min_len/max_len checks and before the URL check, job dir creation and pipeline.run. A bad value gives 422 with detail str(exc). The API always passes `events=` (tuple or None) to pipeline.run, so tests asserting the run kwargs include `'events': None`.
- T-012 (R-003): The job read is a new JSON endpoint `GET /highlights/{job_id}` (route name get_job) returning `{job_id, highlights}` from the stored manifest in manifest (time) order, with optional `?event=` (same comma-list parser; blank = no filter; unknown = 422, checked before the job lookup). Job lookup reuses the get_clip checks through a shared `_manifest` helper (404 'not found'). There is no top on the read. The HTML page /jobs/{id} stays a later task.
- T-012 (R-003): Updating the key-set/kwargs assertions in test_models, test_cli, test_pipeline, test_api, test_t004/t005/t010_acceptance to add event_confidence / events=None follows an intended spec change and does not weaken those tests. Spec updates keep every existing '(updated by T-010)' marker and add '(updated by T-012)'.
