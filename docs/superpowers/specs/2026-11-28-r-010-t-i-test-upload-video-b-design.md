## Design (goal, approaches, choice)

R-010 design. The PO uploaded their own match (job 370c35dc, IMG_3314.MOV, a 38.6-min iPhone recording of about 4.1 GB). They then cleared every segment (job.json is at version 1 with segments []), so the cut was unusable, and goals were the worst part. I could not run ffprobe or the pipeline on that file, so the root causes below come from reading the code and still have to be confirmed on the real file. (1) Fake scoreboard. scoreboard.find_box takes the largest static high-edge component in the top band as 'the scoreboard'. In phone or pitch-side footage that is a fence, a roofline or a stand edge, and every camera pan then counts as a 'score change'. Each change becomes a goal: confidence 0.9 when it is near any audio peak, or a board-only goal at [c-60, c-30] with score 3.0 x priority 5 = 15. That beats every real audio peak, so top-10 fills up with fake goals. Because a box is found, the roar-only fallback is never used. A running match clock (a broadcast filmed off a TV) breaks the same logic: the box never settles, or it changes every minute. (2) Goal clips are cut like every other clip: a 12 s window with 8 s before the loudness peak and 4 s after. The build-up and the shot are often missed, and a long cheer can produce two overlapping 'goal' clips. (3) Weak measurement. The only eval set is an idealised broadcast (clean scoreboard digits without a clock, +20 dB crowd), and goal labels are short. evaluate_dir also calls find_highlights(video) with the default top=10, while pipeline.run uses top=None, so the eval does not score what the product does. (4) Speed. Each run decodes the full video's top band 3 times (tag_goals, tag_incidents.board_reverts, tag_saves) and the audio 4 times. On a 4K/HEVC phone file, scaling the 38-min run to 90 min risks the 10-min budget. GOAL: on footage like the PO's, goal clips are real goals and contain the whole goal moment, and broadcast results do not regress. HOW WE KNOW: `python tests/fixtures/eval_phone/build.py && python -m sportscut eval tests/fixtures/eval_phone --json` reaches goal precision >= 0.8, goal recall >= 0.9 and goal_coverage >= 0.9. The broadcast set `python -m sportscut eval tests/fixtures/eval --json` keeps f1 >= 0.8421 and every per_event value stays the same. pipeline.run decodes the audio once and the top band once. The Tech Lead runs `sportscut cut` on the PO's local job input, before and after, and records in DECISIONS.md the number of goal clips, their reasons and the wall time. No media is committed. APPROACHES: (a) add OCR or a vision model to read the real score and see the ball in the net. That is heavy, breaks the 'optional extras only' budget rule, and still needs a measurement first. (b) Retune the thresholds by eye on the PO's video. There are no labels, so we would be optimising a feeling. (c) CHOSEN: first build a phone/pitch-side synthetic eval set plus a goal-coverage score. Then fix each failure in a small slice that the number can check: reject implausible scoreboards, give goals a goal-shaped window and one clip per goal, accept roar-only goals only for voice-band sound, and decode once. It is the simplest option, needs only ffmpeg and numpy, and every change moves a metric. ASSUMPTIONS: the PO's footage is pitch-side or phone footage with no reliable on-screen scoreboard. The synthetic phone model (a cheer of 7-8 s at about +12 dB, wind gusts below 300 Hz, pans every 60-100 s) is a guess and must be retuned on real labels. NOTE FOR THE PO: to measure your own match, put the video and a labels.csv (start,end,type in mm:ss, e.g. 12:03,12:20,goal) in data/eval/<match-name>/ (git-ignored) and run `python -m sportscut eval data/eval --json`. This changes spec T-013 (board validity, goal windows, roar band) and the T-010/T-013 decision that evaluate_dir calls find_highlights(video), which becomes top=None. Each changing task says so in its brief.
